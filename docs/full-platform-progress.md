## Architectural decisions

- The existing pure Java `game/domain` package remains framework-independent.
- PostgreSQL adapters, security, HTTP and WebSocket code live outside the domain.
- Browser authentication uses Spring Security sessions and CSRF, not browser-stored JWTs.
- CSRF tokens are bound to the server session, fetched from `/api/auth/csrf`, held in frontend memory and attached through the response-provided header name.
- Verification and reset secrets use 256 bits of secure random entropy; PostgreSQL stores only SHA-256 hashes, expiry and one-time-use metadata.
- Unverified accounts may sign in to reach verification status, while suspended and deleted accounts cannot authenticate. Password reset expires every registered live session for the account.
- Match updates are player-specific so active opponent ranks and authoritative piece IDs remain secret.
- REST is the sole authoritative game-command channel. Authenticated STOMP publishes post-persistence safe views to user destinations; the frontend validates match/version sequences and refetches after connect, reconnect or gaps.
- Match snapshots persist absolute deadlines, per-side remaining time, WebSocket presence, disconnect starts, cumulative ranked disconnect duration and a live update sequence. A single injected UTC clock and per-match synchronization determine the earliest immutable outcome.
- Match chat has its own participant-authorized STOMP destinations and persisted sequence. Server-generated IDs/timestamps, fixed lock stripes and a five-message/ten-second limiter preserve single-instance order without coupling chat to authoritative game state. Blocks are bidirectional for delivery and future casual-room joining; reports may reference only the reported opponent's messages from that match.
- Profiles distinguish private account data from public player data. Match history reuses the live safe-view boundary for active participants, discloses complete formations only after termination and gives nonparticipants only result metadata. Ranked results are reconciled into one transactional, exactly-once, zero-sum Elo ledger; leaderboard eligibility and account-status filtering are enforced on the server.
- Ranked matchmaking keeps one insertion-ordered in-memory entry per verified player, expands both players' compatible rating ranges deterministically and persists a two-seat fixed-clock ranked match before atomically removing the pair. A user-scoped STOMP event provides the initial safe view, while status polling recovers missed delivery.
- Current-match recovery is account-authoritative and returns every nonterminal activity, including legacy multiple-open corruption. Casual pre-game cancel/leave actions are versioned, idempotent, snapshot-persisted and published after persistence. `ROOM_CANCELLED` is non-rated and excluded from game statistics; replacement guests receive a fresh chat-visibility cycle.
- The application remains a single Spring Boot modular monolith without Redis or message brokers.

## Blockers and remaining limitations

- Docker API access remains blocked for this local user with `permission denied while trying to connect to the docker API at unix:///var/run/docker.sock`. The compose topology and health checks validate syntactically, and equivalent real PostgreSQL 18, Spring Boot, Vite and Mailpit processes passed the complete browser suite, but `docker compose up` itself and the Testcontainers PostgreSQL test could not run on this host. CI has Docker and executes that coverage.
- The milestone intentionally remains a single-instance modular monolith. It has no Redis/distributed coordination, production SMTP/OAuth, video/voice, timers beyond the documented match clocks, disconnect matchmaking replacement, or frontend administration console.
- Private waiting rooms do not expire automatically. Owners can always cancel them explicitly; a configurable inactivity cleanup policy remains future work.
